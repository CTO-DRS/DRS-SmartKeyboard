# ADR 0003 — سياسة الإصدارات والترقيم: Semver وقنوات التوزيع

- **الحالة:** مقبول
- **التاريخ:** 2026-10-02
- **القرّاء:** الفريق الهندسي
- **النطاق:** كل الإصدارات القادمة من DRS Smart Keyboard

## السياق

الإصدارات تحتاج ترقيمًا آليًا قابلًا للتحقق: بوابات النشر (release.yml
وبوابة `ci/release_checklist.py`) تقرأ `projectVersionName` وتطلب وسمًا
مطابقًا وقيد CHANGELOG، والآلة تحتاج قاعدة صريحة لا تقديرًا بشريًا.

## القرار

### 1. الترقيم: Semver مبسّط `MAJOR.MINOR.PATCH[-prerelease]`

| الشريحة | تُرفع عند |
|---|---|
| `MAJOR` | تغيير بنيوي يكسر التوافق: ترحيل تخزين، تغيير صيغة الحزم، انقلاب واجهة SDK/إضافات |
| `MINOR` | ميزة مستخدم جديدة أو محرك/لغة جديدة (دورة المراحل الربعية) |
| `PATCH` | إصلاحات أعطال وأمان وتحسينات دون ميزات |
| `-betaN` / `-rcN` | إصدارات ما قبل النهائية على قناة البيتا |

الوسم العام دائمًا `v<versionName>` حرفيًا (`v1.0.0`، `v1.1.0-beta3`)، ويُرفض
أي إصدار لا يطابق الوسم `projectVersionName` (بوابة release.yml القائمة).

### 2. versionCode: رتيب صاعد بلا استثناء

- يبدأ من 1 عند الإطلاق الأول العام (v1.0.0) ويزيد **1 على الأقل** مع كل
  إصدار/بيتا يُبنى.
- لا يُعاد استخدام رقم نُشر أصلًا ولو أُلغي الإصدار — الأرشفة لا تُلغي الرقم.
- الإصدارات التجريبية تحتل أرقامًا تسبق الرسمية القادمة (بيتا n+1 قبل 1.1.0).

### 3. مصادر الحقيقة الثلاثة (بوابة آلية تتحقق من انسجامها)

1. `gradle.properties`: `projectVersionCode` + `projectVersionName`.
2. `CHANGELOG.md`: قيد `v<versionName>` للإصدار الجديد (إلا فبوابة الإصدار
   تفشل fail-closed).
3. وسم git عند النشر: `v<versionName>` حرفيًا.

### 4. قنوات التوزيع

| القناة | الأهلية | المصدر |
|---|---|---|
| `release` (مستقر) | إصدارات رسمية بلا لاحقة | وسم `v*` على main |
| `beta` (تجريبي) | لاحقة `-betaN` أسبوعيًا آليًا | `weekly-beta.yml` |
| `debug`/`bench` | تطوير محلي فقط | لا تُنشر |

## العواقب

- أول رقم منفذ في هذه السياسة هو versionCode 1 (v1.0.0).
- بوابة الإصدار [1] هي المنفّذ الآلي للبنود أعلاه؛ أي استثناء يتطلب تعديل
  هذا ADR أولًا.
